### 1-4. MECE 경계 선언 — "이 원칙은 이것을 다루지 않는다"

중복률(SRS) 억제를 위해 각 원칙의 **비범위(out-of-scope)** 를 명시적으로 선언한다.

| 원칙 | 다루는 것 | 다루지 **않는** 것 (다른 원칙으로 이관) |
|:-:|-----------|-------------------------------|
| ① | 정보의 **입력·순환 경로** | 산출물의 형태 → ② / 발행 → ⑦ |
| ② | 학습을 **닫는 산출 규칙** | 산출을 만드는 도구·절차 → ③ / 품질 판정 → ⑤ |
| ③ | 반복 작업의 **절차화·자산화** | 여러 절차의 조립·위임 구조 → ④ |
| ④ | 작업의 **위임 구조 설계** | 위임 결과의 검증 → ⑤ |
| ⑤ | 결과의 **판정 기준과 재시도 루프** | 무엇을 판정할지의 기준점 → ⑥ |
| ⑥ | **차별화 영역의 선택과 축적** | 그것을 밖으로 여는 방법 → ⑦ |
| ⑦ | **공개·피드백·복리** | 공개할 내용물의 생산 → ①~⑥ |

| 일회성 대화 | 재사용 절차 |
|------------|------------|
| 그때그때 다시 쓴다 | 이름이 있다 (`concept-explainer`) |
| 결과가 매번 다르다 | 입력·출력 형식이 고정돼 있다 |
| 잘 됐는지 알 수 없다 | 성공 기준이 문서에 있다 |
| 남에게 못 준다 | 파일로 건넬 수 있다 |
| 개선이 안 쌓인다 | 버전이 올라간다 |

#### 프레임 — 대화를 절차로 승격시키는 4단계 `[슬라이드]`

```
1. NAME    이름을 붙인다        → 부를 수 있어야 재사용된다
2. SLOT    변하는 부분을 뚫는다  → {주제} {대상} {길이}
3. SHAPE   출력 형태를 고정한다  → "표 3열 / 각 셀 20자 이내"
4. CHECK   성공 기준을 적는다    → "전문 용어가 살아 있는가?"
```

> `[멘트]` "이 4단계를 통과하면 프롬프트가 아니라 **스킬**이 됩니다. 여러분이 방금 만든 건 텍스트가 아니라 도구예요.
> 그리고 도구는 서랍에 넣어둘 수 있습니다. 대화는 못 그러죠."

#### 승격 판정 기준 `[슬라이드]`

> **"두 번 쓸 것 같으면, 그 자리에서 절차로 만들어라."**
> 세 번째에 만들면 이미 두 번을 낭비한 것이다.

#### 앵커 사례 `[슬라이드 + 라이브 링크]`

**PCH-Optimizer — 프롬프트를 운영체제로 승격시킨 사례**
→ https://reasonofmoon.github.io/2026/06/22/pch-optimizer-operating-system/

`[슬라이드]` 승격의 실물 지표:

```
115개 카탈로그 항목 → 8개 커널 원리 + 7개 프롬프트 유형(T1~T7)
6단계 파이프라인: CLASSIFY → DIAGNOSE → ENGINEER → ASSEMBLE → VERIFY → HANDOFF
```

> `[멘트]` "여기 8개 커널 원리 중에 이런 게 있습니다 — **'모델과 하네스를 분리한다'**, 그리고 **'신뢰보다 검증'**.
> 오늘 남은 두 챕터(④⑤)에서 우리가 할 이야기가 이미 여기 박혀 있는 거죠."

- 절차화 방법론: [프롬프트 기법 메뉴를 하네스로 바꾸는 법](https://reasonofmoon.github.io/2026/06/22/pch-optimizer-technique-menu/)
- CHECK 단계 실례: [좋은 프롬프트는 진단표와 검증표를 함께 가진다](https://reasonofmoon.github.io/2026/06/22/pch-optimizer-diagnostic-rubric/)

**단일 프롬프트의 절차화 예시 (SHAPE + CHECK가 명시된 형태)**
→ [전문 용어를 잃지 않는 쉬운 설명 프롬프트](https://reasonofmoon.github.io/2026/06/24/concept-explainer-prompt-terms/)

**흩어진 대화 → 지식 노드 전환 (앞의 478개 이야기의 결말)**
→ [Claude Archives를 LLM Wiki로 복원하기](https://reasonofmoon.github.io/2026/07/03/claude-archive-llm-wiki-registry/)

- 473개 파일을 **11개 작업 계열**로 정렬 (영어교육·원서학습 73 / 시험·문항생성 31 / 글쓰기·출판 35 …)
- 원칙 선언: **"프롬프트를 보존하지 말고, 프롬프트가 해결하던 문제를 보존한다"**

> `[멘트]` "Hook에서 던진 478개, 기억나시죠. 저 사람은 그걸 버리지 않고 **11개 계열로 정렬**했습니다.
> 그때 쓴 문장이 이겁니다 — '프롬프트를 보존하지 말고, 프롬프트가 해결하던 문제를 보존한다.'
> 이게 오늘 4단계의 요약입니다. 우리는 문장을 저장하는 게 아니라 **문제를 저장**하는 겁니다."

#### `[발표자 노트]` 강연자 힌트

- Hook의 473이라는 숫자를 반드시 3-6 섹션에서 회수할 것. 열고 안 닫으면 원칙 ②를 강연자가 위반하는 셈.
- NAME→SLOT→SHAPE→CHECK는 판서로 하나씩 쓰면서 진행. 한 번에 4개를 슬라이드로 던지지 말 것.
- 새 개념 4개는 인지 부하 상한이다. 여기서 "스킬 파일 포맷" 같은 세부는 절대 꺼내지 말 것 (④로 이관).
- 청중이 개발자가 아닐 경우, SLOT을 "메일 템플릿의 [고객명]"으로 비유하면 즉시 통한다.

### 3-2. 실습 페이지 (Step 2) — 프롬프트 1개 승격시키기

#### 워크시트 구조 `[실습]`

**Part A. 후보 고르기 (3분)**

- ☐ 최근 2주 안에 **두 번 이상 비슷하게 쓴 요청**을 1개 떠올렸다
- `[실습]` 그 요청을 한 문장으로: `________________`

**Part B. 4단계 승격 (12분)** — 각 단계 텍스트 입력

| 단계 | 입력 항목 | 플레이스홀더 |
|------|----------|-------------|
| 1. NAME | 절차 이름 (영문 kebab-case 권장) | `weekly-report-writer` |
| 2. SLOT | 변수 3개까지 | `{기간}` `{대상독자}` `{강조포인트}` |
| 3. SHAPE | 출력 형태 명세 | "H2 3개 / 각 섹션 불릿 3개 / 총 400자 이내" |
| 4. CHECK | 성공 기준 2~3개 | "수치가 반드시 포함될 것 / 사내 용어를 풀어쓰지 말 것" |

**Part C. 저장 위치 지정 (3분)**

- `[실습]` 이 절차를 어디에 두는가? (드롭다운) — `프롬프트 노트` / `스킬 파일` / `스니펫 도구` / `기타`
- `[실습]` 다시 꺼낼 때 검색할 키워드 1개: `________`

**Part D. 즉시 실행 (2분)**

- ☐ 완성된 절차를 실제로 1회 실행해 봤다
- ☐ 실행 결과가 CHECK 기준을 통과했다 (통과/미통과 라디오 + 미통과 시 수정 메모란)

#### 완료 조건 / 채점

```js
const complete =
  candidate.length > 0 &&
  promotion.name && promotion.slots.length >= 1 &&
  promotion.shape && promotion.check.length >= 2 &&
  storage.location && partD.executed === true;
// XP 140 · CHECK 미통과 후 수정 메모까지 작성 시 보너스 +20 (실패 기록 장려)
```

### 3-3. 디브리핑 3문항 `[슬라이드]`

- **Q1.** SLOT을 뚫으면서 "이건 사실 안 변하는 값이었네"라고 깨달은 게 있나요?
- **Q2.** CHECK 기준을 쓰기가 SHAPE보다 어려웠나요, 쉬웠나요? 그 이유는?
- **Q3.** 이 절차를 지금 옆 사람에게 파일로 건넨다면, 그 사람이 그대로 쓸 수 있을까요?

### 3-4. Q&A 예상

| 예상 질문 | 응답 방향 |
|----------|----------|
| "모델이 바뀌면 프롬프트가 무용지물 아닌가요?" | NAME/SLOT/SHAPE/CHECK 중 모델 종속적인 건 거의 없다. 문장 표현만 갱신되고 **구조는 남는다** |
| "절차를 몇 개나 만들어야 하나요?" | 개수 목표를 두지 말 것. '두 번 규칙'만 지키면 필요한 만큼만 생긴다 |
| "CHECK를 AI가 대신 써줘도 되나요?" | 초안은 가능. 다만 최종 CHECK는 **내 판단 기준**이어야 하고, 이게 ⑤와 ⑥의 재료가 된다 |

### 4-1. 설명 페이지 (Step 1)

#### Hook `[멘트]`

> "AI에게 일을 맡겼는데 엉뚱한 걸 가져온 적, 다들 있으시죠.
> 그때 우리가 하는 일은 보통 이겁니다 — **프롬프트를 더 길게 씁니다.**
> 그리고 다음번엔 더 길게 씁니다. 그러다 프롬프트가 A4 세 장이 됩니다.
> 여기서 질문. 프롬프트가 세 장이 됐다는 건, 프롬프트가 부족했다는 신호일까요?
> ...아닙니다. **그건 프롬프트가 감당할 수 있는 크기를 넘어섰다는 신호입니다.**"

#### 오해 깨기 `[슬라이드]`

```
❌ AI가 알아서 잘 해주면 된다 (방목)
✅ AI가 벗어날 수 없는 길을 만든다 (하네스)
```

#### 핵심 대비 구조 `[슬라이드]`

| 방목 (위임) | 하네스 (구조 설계) |
|------------|------------------|
| "이거 잘 좀 해줘" | 역할·입력·산출·경계가 문서화돼 있다 |
| 실패하면 다시 부탁한다 | 실패하면 **어느 단계**에서 깨졌는지 보인다 |
| 결과가 사람에 따라 다르다 | 누가 돌려도 같은 형태가 나온다 |
| 규모를 못 키운다 | 단계를 붙여 규모를 키운다 |
| 프롬프트가 길어진다 | 프롬프트가 **쪼개진다** |

#### 프레임 — 하네스 3부품 `[슬라이드]`

```
1. 역할 분할 (WHO)   한 명에게 다 시키지 않는다
                     → 설계자 / 실행자 / 검사자
2. 절차 배선 (HOW)    ③에서 만든 절차들을 순서로 잇는다
                     → 입력 → 단계1 → 단계2 → 산출
3. 경계 선언 (WHERE)  하지 말아야 할 것을 먼저 적는다
                     → "이 범위 밖은 손대지 않는다"
```

> `[멘트]` "여기서 가장 자주 빠뜨리는 게 3번, **경계**입니다.
> 사람들은 '무엇을 하라'만 적고 '무엇을 하지 마라'를 안 적어요.
> 그런데 AI가 사고 치는 건 거의 항상 **적지 않은 영역**에서 일어납니다."

#### 분해 판정 — Tool? Skill? Subagent? `[슬라이드]`

| 신호 | 처방 |
|------|------|
| 매번 같은 조작을 반복한다 | **Tool** (도구화) |
| 같은 종류의 판단을 반복한다 | **Skill** (절차화 — 원칙 ③) |
| 판단의 **맥락 자체**가 달라진다 | **Subagent** (역할 분리) |
| 프롬프트가 A4 2장을 넘겼다 | 무조건 분해 신호 |

- `[실습]` 이 업무의 최종 산출물은 무엇인가: `________________`

**Part B. 역할 분할 (7분)** — 3행 입력표

| 역할 | 이 역할이 하는 일 | 이 역할의 산출 |
|------|-----------------|---------------|
| 설계자 | (입력) | (입력) |
| 실행자 | (입력) | (입력) |
| 검사자 | (입력) | (입력) |

> 안내문: "3개를 다 채우기 어렵다면, 그 업무는 아직 하네스가 필요 없을 수도 있습니다. 더 큰 업무로 바꾸세요."

**Part C. 절차 배선 (8분)** — 단계 카드 추가형 (최소 3, 최대 6)


각 단계 카드에 입력 항목: `단계명` / `쓰는 절차(③에서 만든 것 재사용 가능)` / `이 단계의 완료 조건`

**Part D. 경계 선언 (5분)** — 자유 입력 3줄 (필수)

- `[실습]` 하지 않을 것 1: `________________`
- `[실습]` 하지 않을 것 2: `________________`
- `[실습]` 사람이 반드시 개입하는 지점: `________________`

**Part E. 분해 판정 (2분)** — 체크리스트

**Part D. 7주 루프 예약 (2분)**

- `[실습]` 앞으로 7주간 매주 공개할 것 (원칙 ①~⑦ 순서 자동 제안, 편집 가능)

### 7-3. 디브리핑 3문항 `[슬라이드]`

- **Q1.** 공개를 망설이게 하는 진짜 이유는 무엇입니까 — 완성도, 반응, 아니면 시간?
- **Q2.** '반박 초대' 문장을 붙이니 기분이 어떻습니까? 불편하다면, 그 불편이 바로 복리의 비용입니다.
- **Q3.** 7주 뒤 회고에서 당신이 발견하고 싶은 것은 무엇입니까?

### 7-4. Q&A 예상

| 예상 질문 | 응답 방향 |
|----------|----------|
| "회사 일이라 공개가 안 됩니다" | 도메인 사실을 빼고 **구조만** 공개하면 된다. 하네스 설계도는 대부분 기밀이 아니다 |
| "아무도 안 보면요?" | 초기엔 안 본다. 복리의 1~2주차는 원래 평평하다. **보는 사람 0명이어도 ②의 닫힘 효과는 그대로 남는다** |
| "SNS를 꼭 해야 하나요?" | 아니다. 접근 경로 1개면 충분하고, 팀 채널도 공개다 |
| "틀린 걸 올리면 창피한데요" | 틀린 채로 노트에 두는 것과, 틀린 채로 공개해 고치는 것 중 뒤가 빠르다. 그래서 반박 초대가 3레버에 있다 |

### 7-5. 슬라이드 아웃라인 (9장)

1. 챕터 표지 — 원칙 ⑦
2. 학습 목표 2개

5. 공개 루프 3레버 (주기 / 경로 / 반박 초대)
6. "전시는 박수를 받고, 공개는 지적을 받는다"
7. 공개 최소 단위 4단계 표
8. **앵커 라이브** — reasonofmoon.github.io + 원칙 ①~⑦ 매핑표 (시리즈 회수 슬라이드)
